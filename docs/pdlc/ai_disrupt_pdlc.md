# AI-Disrupt PDLC Framework: Регламент разработки проекта

> Регламент внедрения концепции **AI-Disrupt PDLC** (AI-Disrupted Product Development Life Cycle) для команды разработки программного комплекса «Агент: ИИ система для протоколирования совещаний Министерства образования».

---

## 1. Суть концепции AI-Disrupt PDLC в проекте

В традиционном цикле разработки (SDLC) узким горлышком является написание и рефакторинг кода человеком.  
В модели **AI-Disrupt PDLC** написание кода делегируется ИИ-агентам и кодогенераторам, а ключевая ценность и рабочее время инженера смещаются **вверх по цепочке** — в формулирование замысла, детальную спецификацию требований, проверку граничных условий и верификацию.

### Двухконтурная модель (The Two-Loop Model):

```
┌────────────────────────────────────────────────────────────────────────┐
│                   1. КОНТУР ЗАМЫСЛА (Intention Loop)                   │
│                       Человек (Инженер / Тимлид)                       │
│  - Архитектурные контракты и ограничения ИБ                            │
│  - Спецификации OpenSpec (EARS / BDD: GIVEN-WHEN-THEN)                 │
│  - Проектирование граничных случаев и критериев приёмки (DoD)          │
└───────────────────────────────────┬────────────────────────────────────┘
                                    │ Промпт + Контекст + Спецификация
                                    ▼
┌────────────────────────────────────────────────────────────────────────┐
│                2. КОНТУР РЕАЛИЗАЦИИ (Implementation Loop)               │
│                        ИИ-агенты / LLM-ассистенты                      │
│  - Генерация бойлерплейта, Pydantic-схем, роутов FastAPI               │
│  - Генерация React-компонентов и состояний редактора                   │
│  - Написание unit- и интеграционных тестов                             │
│  - Синтез тестовых стенограмм и датасетов для QA                       │
└───────────────────────────────────┬────────────────────────────────────┘
                                    │ Код + Тесты
                                    ▼
┌────────────────────────────────────────────────────────────────────────┐
│                  3. АВТОМАТИЧЕСКИЕ РЕЛЬСЫ (Guardrails)                 │
│                 Линтеры, MyPy, Pytest, Security Scanners               │
│  - Код принимается только при 100% прохождении тестов и типов          │
│  - Review человеком фокуса логики, а не синтаксиса                     │
└────────────────────────────────────────────────────────────────────────┘
```

## 2. Матрица трансформации ролей команды (5 человек)

| Роль | Традиционный подход | AI-Disrupt подход (Наша практика) |
|---|---|---|
| **Team Lead / Architect** | Распределение тикетов, ручной code review каждой строчки | **Context & Guardrails Owner:** проектирование системных промптов, OpenSpec-контрактов, контроль контура ИБ и архитектурной чистоты |
| **AI / ML Engineer** | Ручное написание пайплайнов обработки аудио с нуля | **AgentOps & Model Tuning:** настройка локальных моделей (GigaAM, Saiga), использование AI для автогенерации бенчмарков и замеров latency/VRAM |
| **Backend Engineer** | Ручная набивка CRUD, DTO и шаблонных тестов | **AI-Augmented Architect:** формулирование Pydantic-контрактов, генерация сервисов через AI, фокус на сложной бизнес-логике и RAG |
| **Frontend Developer** | Ручная верстка компонентов по Figma пиксель-в-пиксель | **AI-Augmented UX:** генерация UI-компонентов (Tailwind/React) через AI, фокус на эргономике работы секретаря и обработке состояний |
| **QA / AI Evaluator** | Ручное составление тест-кейсов и кликанье интерфейса | **Synthetic Data & Evals Architect:** генерация синтетических стенограмм с помощью LLM, автоматизация бенчмарков DeepEval/Ragas |

## 3. Практический пайплайн работы над задачей (AI-Spec-Driven Workflow)

Каждая задача из `openspec/changes/001-initial-protocol-agent/tasks.md` выполняется строго по 5 шагам:

1. **Step 1: Specification (Intention):**
   Разработчик не пишет код «из головы». Сначала формулируется спецификация в `openspec/specs/` (входные данные, сценарии BDD `GIVEN / WHEN / THEN`).
2. **Step 2: Context Injection:**
   Разработчик передает ИИ-ассистенту:
   - Контекст проекта из `openspec/config.yaml`;
   - API-контракт `backend/app/schemas/api_contract.py`;
   - Спецификацию задачи.
3. **Step 3: AI Generation (First Pass):**
   ИИ генерирует черновой код модуля и **сразу набор тестов к нему**.
4. **Step 4: Deterministic Guardrails (Проверка рельсами):**
   Запуск локального тестирования (`uv run pytest`, `uv run ruff check`, проверка типов `uv run mypy`). ИИ исправляет ошибки компиляции/типизации до тех пор, пока тесты не станут «зелёными».
5. **Step 5: Human Semantic Review:**
   Инженер проверяет соответствие кода замыслу, отсутствие галлюцинаций в логике и производительность.

## 4. Политика информационной безопасности при использовании ИИ разработчиками

> [!CAUTION]
> **Категорически запрещено:**
> 1. Отправлять в публичные облачные AI-инструменты (ChatGPT, Claude Cloud, Copilot) реальные аудиозаписи совещаний, служебные стенограммы или персональные данные сотрудников Министерства.
> 2. Использовать реальные ведомственные протоколы в облачных промптах.

### Разрешённые практики:
- Для генерации кода использовать обезличенные интерфейсы, синтетические данные и общедоступные библиотеки.
- Тестирование и бенчмаркинг пайплайнов извлечения фактов проводить строго на **локальных/on-prem инстансах моделей** или на синтетическом датасете, подготовленном QA-инженером.
